01
Capabilities

Agent 到底能做什么，
不能做什么

Host Agent 的能力分成发现、观测、解释、受控执行四层。它的价值不是“能跑命令”，而是“在机器上形成可复核的证据，并把结论带回平台”。

框架说明：客户端是轻量 Go LLM Agent：内置 CloudWeGo Eino ADK Runtime（Wake → Context → Plan → Act → Verify → Report → Sleep），模型走服务端 LLM Gateway；不是 dsh on host，也不是纯主机代理。服务端 Commander 使用 dsh，负责下发 Profile/Directive/DeployOrder 与最终审批。
能力具体做什么边界
受控发现OS/发行版/内核、systemd、包、用户、端口、进程、容器元数据、应用指纹、部署方式、配置/日志路径、运维工具客户端、已有依赖只读、限路径、限时；不做端口扫描、不读密钥、不执行应用代码
应用画像判断应用服务器/数据库/中间件/运维工具客户端；记录部署方式、配置路径、日志路径、端口、启动用户、版本、置信度低置信度只作候选；不自动绑定应用系统/数据中心
归属与本地知识IP/主机名/CMDB 匹配应用系统与数据中心；本地保存副本、置信度、更新时间服务端是主数据；冲突进入复核
常驻观测5s 资源/进程、30s 服务/端口/连接/应用健康、5m 配置哈希/日志签名/依赖变化最长 1 天；1GB/2% 硬上限；不做长期本地趋势
异常上报本地阈值/基线/连续次数；聚合、去重、带快照与证据上报不直接触发破坏性动作；避免告警风暴
本地 CLI类似 Claude Code 的对话：状态、发现、日志、诊断、报告；模型走服务端 Gateway普通用户权限；R2+ 不能本地批准
受控诊断日志尾、线程栈、连接/端口、配置片段、服务状态、诊断包动作注册表；路径/参数白名单；输出上限
本地 LLM 分析巡航/异常触发：上下文 + 只读工具 + 计划/验证/报告；模型走服务端 Gateway≤8–12 步/预算；空闲不调模型；不持有模型 Key
受控部署/升级签名 DeployOrder/制品、预检、停/换/启、健康检查、canary、回滚R3；变更单/维护窗口/审批；只执行注册动作
证据回传结果带采集时间、主机、应用、来源、哈希、置信度、脱敏标记不把原始全量日志持续回传；按需/窗口
安全接入一次性令牌、CSR、mTLS、证书轮换、签名指令、防重放只出站；0 入站端口
自我约束CPU/内存/IO 限额、磁盘预算、心跳、退避、降级、隔离不影响业务；异常时先自限流

默认允许 · 只读 / 诊断

  • 发现 OS/服务/应用/配置/日志位置
  • 指标、服务状态、端口/连接、进程
  • 日志尾部、错误签名、配置片段（脱敏）
  • 线程栈、GC/堆摘要、诊断包
  • 本地对话、报告、知识缓存

默认禁止 / 必须审批

  • 启动/停止/重启服务、kill 进程
  • 写配置、删文件、装包、改内核/防火墙
  • 读密钥/私钥/完整环境变量
  • 任意 Shell、任意文件读取
  • 端口扫描、横向访问、部署/升级（P3 前）
Agent 不是“主机上的 root Shell”。默认 root 是为了读取 /proc、systemd、journald、包信息；所有写/执行都必须经过动作注册表、签名指令和 R0–R3 审批。

// Agent → 服务端（签名结果 + 证据） { "command_id": "cmd_01J9...", "host_id": "host_8f2a", "state": "ok", "evidence": [{ "kind": "log_tail", "at": "...", "source": "/var/log/order/service.log", "hash": "sha256:...", "redacted": true }], "summary": "HikariPool timeout; 42 waiters", "signature": "ed25519:..." }

协调的 6 条规则

01
Commander 决策，Agent 执行

Commander 不直接执行主机命令；Agent 不决定事件是否关闭/是否需要审批。

02
证据必须可追溯

每条结论引用来源、时间、哈希、命令 ID；没有证据的假设只作为待验证。

03
并行取证，串行裁决

Host/Connector/Specialist 可并行；根因/审批由 Commander 统一收敛。

04
失败显式

Agent 离线/超时/权限失败必须上报；不允许“假成功”或静默重试。

05
权限不放大

Commander 不能因为“指挥”获得 Agent/连接器之外的权限；R2+ 仍走审批。

06
人类可接管

暂停/改派/确认根因/终止；接管记录进事件时间线。

不要用“模型直接指挥 shell”替代这套机制。没有 Ticket/Evidence/Approval 的“多 Agent 对话”无法审计、无法回滚、也无法证明根因。
06
Playbooks

五个真实排障/部署场景，
看 Agent 和 Commander 怎么配合

下面用五个典型故障/部署说明“谁在什么时候做什么、证据从哪里来、什么必须审批”。示例是设计推演，不是生产数据。

示例 A · 数据库连接池耗尽

订单服务 5xx：连接池 92%，等待队列 47

告警来自 Zabbix/Prometheus；涉及应用主机、MySQL、连接池配置和最近变更。

0s · Alert Zabbix 告警：order-service 5xx 4.8%，连接数 92%。AlertSource 去重后建 Incident，严重度 P1。Commander：定级，拆 Ticket：主机、连接池、DB、变更。
5s · Host HostAgentExecutor 下发 diag.snapshot + diag.log_tail + diag.config_read 到 order-app-12。Agent：发现应用 systemd、配置路径、日志路径；读取脱敏配置片段。
15s · Connector Prometheus 查 hikaricp_connections_pending；MySQL 查 processlist/max_connections；变更记录查最近 30 分钟。证据：等待队列从 3 → 47；连接池 max=50；30 分钟前发布过配置。
30s · Evidence 证据板：应用日志 HikariPool timeout；线程栈 42 个等待；配置 hash 变化；连接数曲线。Hypothesis A：连接泄漏；Hypothesis B：连接池上限过低；Hypothesis C：DB 端连接被占满。
60s · Commander 交叉验证：DB 端连接正常，应用端连接只增不减，变更含连接池参数。根因置信度 0.86：连接池参数/释放逻辑导致耗尽；建议回滚或扩容连接池。
2m · Approval R2：回滚配置/重启应用；企业微信审批卡片；审批人确认维护窗口。拒绝则只输出报告；批准后 Agent 执行受控重启，记录回滚点。
5m · Verify Agent 回传重启后 5xx/连接数；Connector 复查；Incident 关闭；知识草稿“连接池耗尽排查/回滚”。
这个场景里：Host Agent 提供“机器上到底发生了什么”；Connector 提供“平台侧指标/DB 视角”；Commander 负责把两者对齐并给出可审批的结论。
示例 B · K8s 节点磁盘压力

node-prod-07 磁盘 91%，Pod 被驱逐

涉及节点、kubelet、容器运行时、日志/镜像占用、容量策略。

0s K8s/Node 告警；Incident P1；Commander 拆“节点、容器、日志/镜像、容量策略”四个 Ticket。
10s Host Agent：df、节点 systemd、kubelet 日志、容器运行时元数据、目录占用（限路径/限深）。
20s Connector：K8s 节点/Pod 状态；Prometheus 磁盘曲线；变更记录。
40s Evidence：/var/lib/containerd 镜像层增长；日志轮转失败；imagefs 阈值触发。
2m 方案：清理旧镜像/日志（R2）或扩容（R3）；先审批清理；保留回滚点；不自动 drain 节点。
5m 清理后复查；若仍高，升级为扩容变更；知识草稿“节点 imagefs 压力处理”。
示例 C · 发布后配置错误

支付网关超时：配置 hash 变了，但代码没变

典型的“变更相关故障”；主机证据 + 变更记录比单看指标更快。

0s 支付网关超时告警；Incident P1；Commander 优先查“最近变更”。
10s Host Agent：配置路径/最后修改时间/脱敏 diff、服务状态、连接/线程、日志错误签名。
20s 变更系统：10 分钟前配置发布；Connector：超时从发布后 1 分钟开始。
40s 证据对齐：配置项 timeout=200ms（原 2s）；Hypothesis 明确；建议回滚配置。
2m R2 回滚审批；Agent 不直接改配置，执行受控回滚/重启；验证超时恢复。
5m 报告 + 知识：把“变更 → 配置 hash → 日志签名 → 指标”写成案例。
示例 D · Agent 离线 / 网络分区

主机 Agent 心跳丢失，但业务仍在跑

应急场景最怕“没有证据却假装有结论”；平台必须显式降级。

0s Agent 心跳超时；Gateway 标记 degraded；Incident 追加“主机证据缺失”。
10s Commander 不假设主机状态；改用 Prometheus/Zabbix/日志平台/其他主机证据；优先级提高。
30s 如需本机数据，触发带外/人工检查；不能伪造 Host Agent 回执。
2m 根因结论标注“主机侧未验证”；审批只允许低风险动作；报告明确证据缺口。
恢复 Agent 重连后补采快照；事件复审；避免重复告警。
示例 E · 受控部署/升级

订单服务 v2.4.1：签名 DeployOrder，canary 10%

不是 Agent 自己决定发布；服务端下发标准、制品和策略，Agent 只执行注册的部署动作。

0s · Order 服务端生成签名 DeployOrder：应用/版本/制品 digest/目标主机/维护窗口/canary 10%/回滚版本；R3 审批通过。
10s · Preflight Agent 校验签名/租户/主机/制品 digest；检查磁盘、端口、依赖、当前版本、健康基线；不通过即 abort。
30s · Canary 停止一个实例 → 替换制品/配置 → 启动 → 健康检查（端口/HTTP/日志/指标）；失败自动回滚并上报。
2m · Observe Agent 回传 canary 证据；Commander/连接器对比错误率/延迟/资源；人确认后放量。
5m · Rollout 分批滚动；每批健康检查；Agent 记录部署动作/版本/证据；失败停止并回滚。
完成 部署记录、变更单、证据、报告；知识草稿“v2.4.1 发布/回滚”。
边界：DeployOrder 不能携带任意 Shell；Agent 只执行 deploy.preflight/deploy.apply/deploy.health/deploy.rollback 等注册动作；制品必须签名校验。
07
Boundaries

应急也要有边界，
否则“智能”就是风险

排障越紧急，越需要明确“谁能做什么”。Agent 默认只读；Commander 默认不执行；R2/R3 都必须有人类审批和回滚点。

级别示例执行条件审计
R0 只读status、metrics、日志尾、配置片段、端口/连接、线程栈本地策略允许动作/参数哈希/结果摘要
R1 低危诊断包、快照、一次额外采集本地策略 + 服务端任务任务 ID + 产物
R2 高危重启服务、清理临时文件、切日志级别、回滚配置签名指令 + 人工审批 + 回滚点全程审计 + 回执
R3 变更部署、升级、扩缩容、改网络/内核变更单 + 维护窗口 + 双人审批变更单 + 回滚
Root
默认 root + 门控

采集需要 root；但动作注册表、路径/参数白名单、无裸 Shell、写路径最小化、root 审计。

Signed
签名指令

mTLS + KMS/HSM 签名 + nonce/过期 + command_id 幂等 + 主机/租户二次校验。

Human
人工 break-glass

紧急情况由人通过 SSH/跳板机操作；不把“紧急”变成 AI 的任意 shell。

三个绝不：绝不把日志/告警文本拼成 Shell；绝不让 Commander 绕过审批执行 R2+；绝不用“模型说没事”替代证据。
08
Failure modes

Agent 不在、证据冲突、
审批超时怎么办

排障系统必须能处理“证据不完整”的状态，而不是强行给一个根因。失败要显式、可重试、可接管。

失败平台行为Agent 行为
Agent 离线/心跳丢失标记 degraded；Incident 记录证据缺口；改用连接器/其他主机；不伪造回执重连后退避；补报；不无限重试
指令超时Assignment timeout；重试/换动作；必要时人工接管取消本地动作；保留已产生证据
证据冲突保留多源证据；Hypothesis 不强行收敛；请人确认上传原始引用/时间/哈希
审批超时/拒绝R2 不执行；Incident 记录；可转人工/变更窗口保持只读；不绕过
指令伪造/重放Gateway 拒发/审计；告警签名/tenant/host/nonce 校验失败即拒
插件查询失败标记证据缺失；重试/回源/降级不相关

建议观测指标

≤ 30s首条主机证据（目标）
≤ 2s指令下发到 Agent 回执（目标）
100%R2+ 审批覆盖
<1%Agent 空闲 CPU

指标是设计目标，需要在 G9/G10 与生产灰度中校准；不以指标替代证据。

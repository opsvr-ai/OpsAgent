01
Positioning

不是远程 Shell，
而是服务器上的受控操作员

服务器 Agent 的价值不在于“能执行多少命令”，而在于它能在本地完成发现、观测和初步诊断，同时把所有越界动作收回到服务端的策略与审批里。

它由四部分组成：一个常驻守护进程、一个本地 CLI、一个本地知识与快照库、一个只读优先的执行器。服务端负责身份、策略、指令签名、工具编排和总控智能体；Agent 负责在主机上“看见、记住、解释、回传”。

Discover
本地发现

操作系统、服务、应用部署方式、配置与日志位置，形成可复核的应用画像。

Observe
常驻观测

小颗粒度指标与状态快照，本地留存短周期，异常时带证据上报。

Act
受控执行

只执行注册过的动作；读操作默认允许，写操作需要签名指令与审批。

Explain
证据回传

把“为什么判断异常”连同采样、配置、日志片段一起交给服务端。

边界先于能力。Agent 的能力不是靠文档约束，而是靠三件事同时约束：初始能力包、服务端策略、执行器动作注册表。任何一条不满足，动作就不可执行。

三条设计底线

01
不开放入站

Agent 主动向 Gateway 建立 mTLS 长连接。没有反向端口、没有公网监听、没有“服务端随时 SSH 进来”。

02
不执行裸 Shell

服务端下发的是动作 ID + 结构化参数。执行器按注册表校验，不把自然语言或日志内容拼成命令。

03
不自动做危险动作

发现、采集、诊断默认只读；重启、改配置、装包、升级属于 R2/R3，必须审批与可回滚。

02
Lifecycle

从“被安装”到“被信任”，
中间有明确的 Gate

Agent 不应该在安装完成的一瞬间就拥有完整能力。初始化阶段先证明“我是谁、我在哪、我看见了什么”，再进入常驻观测。每一步都有可验证的产物。

01

安装与自检

释放二进制、systemd unit、目录与最小权限；自检 CPU/内存/磁盘/时钟/网络连通性；不读取业务数据。

只读无凭据
02

注册与身份

使用一次性加入令牌换取 CSR 签名，拿到设备证书；绑定主机名、IP、租户与数据中心；随后拉取签名策略/技能包/工具包。

mTLS证书轮换签名包
03

受控发现

按能力包扫描有限路径：systemd、包管理、监听端口、进程、容器元数据、配置/日志位置；生成带证据的 DiscoveryReport。

只读有限路径
04

应用归属

用 IP/主机名/CMDB 匹配应用系统与数据中心；多候选时保留置信度，交服务端或人确认，不强行绑定。

本地知识冲突可审计
05

基线建立

采集 24–72 小时基线：服务集合、端口、进程、资源曲线、日志错误签名；避免把“正常波动”当异常。

短周期本地
06

常驻自巡航

按节奏采集指标、服务状态、应用健康与配置漂移；异常本地聚合、去重、带快照上报。

只读默认低开销
07

受控排障

服务端总控智能体下发诊断动作；Agent 执行只读检查、收集证据、给出本地结论；涉及写操作进入审批。

签名指令幂等
08

扩展与升级

技能包/工具包热更新；二进制签名升级、灰度、回滚；未来部署/升级能力沿用同一套策略。

签名包R3 预留

03
Discovery

先发现，再判断，
最后才允许“上报为知识”

初始化阶段最重要的不是“采到最多”，而是“用最小侵入建立一张可复核的应用画像”：这台机器上跑了什么、怎么部署、配置在哪、日志在哪、出问题先看哪里。

应用服务器 vs 运维工具客户端 vs 数据库/中间件

Application
应用服务器

有业务端口、业务配置、业务日志、应用进程；例如 Spring Boot、Node、Go 服务、Tomcat、Nginx 反向代理。

Ops client
运维工具客户端

以“采集/转发/执行”为目的：Zabbix Agent、node_exporter、filebeat、telegraf。它们本身不是业务应用。

Data / middleware
数据库与中间件

MySQL、PostgreSQL、Redis、ClickHouse、Kafka 等；按数据服务单独建模，不与业务应用混为一谈。

识别采用“多信号 + 置信度”，不靠单一进程名。比如：java -jar order-service.jar + 监听 8080 + systemd unit + 配置/日志路径，才判定为应用实例；只有 java 进程不构成结论。

Evidence
每条结论必须带证据

进程 cmdline、unit 文件路径、端口、配置路径、日志路径、包版本、发现时间。没有证据的猜测只作为“候选”，不写入正式知识。

Confidence
低置信度不自动绑定

多候选应用系统/数据中心时，标记 ambiguous，保留候选与理由，交服务端匹配或人工确认。

DiscoveryReport 摘要

// 本地生成，签名后上报；正文不包含密钥 { "host": { "hostname": "order-app-12", "ip": "10.20.8.12", "os": "Rocky Linux 9.4" }, "app_candidates": [{ "name": "order-service", "type": "java-springboot", "deploy": "systemd", "ports": [8080], "config": ["/opt/order/conf/application.yml"], "logs": ["/var/log/order/service.log"], "confidence": 0.92, "evidence": ["systemd:order.service", "proc:cmdline"] }], "ops_clients": ["zabbix-agent2", "node_exporter"], "binding": { "app_system": "订单中心", "dc": "华东-1", "confidence": 0.86 } }

应用归属：IP/主机名不是唯一真相

服务端按“显式标签 → CMDB IP/网段 → 主机名规则 → 人工确认”的顺序匹配应用系统与数据中心。Agent 把结果和候选一起写入本地知识，离线时仍能回答“这台机器属于谁”。IP 变更、迁移、克隆时，旧绑定不会被静默覆盖，而是进入复核队列。

本地知识是缓存，不是主数据。服务端是应用系统/数据中心的主数据源；Agent 本地保存的是“可离线使用的副本 + 置信度 + 更新时间”，冲突时以服务端复核结果为准。
04
Collection

小颗粒度采集，
但必须被磁盘预算驯服

常驻采集的目标是“异常发生时，有足够细的现场”，不是“把所有数据搬回服务端”。细粒度数据留在本地环形缓冲区，服务端只接收摘要、异常窗口和按需拉取的快照。

频率采集本地保留是否上传
5sCPU、内存、load、磁盘 IO、网络吞吐、进程 TopN2 小时否，异常窗口才带出
30s服务状态、监听端口、连接数、应用健康、线程/队列关键指标24 小时摘要 + 异常
5m配置哈希、日志错误签名、依赖变化、版本/包变化24 小时变化 + 摘要
on-demand进程栈、日志尾部、连接详情、配置片段、诊断包24 小时 / 200MB仅任务结果
Disk guard
硬上限：1GB 或磁盘 2%

取更小值。超过 80% 时删最旧的高频数据；超过 95% 暂停高频采集，只保留服务状态与异常，并上报告警。不允许 Agent 把磁盘写满。

Local first
快照在本地，按需上传

zstd 压缩、列式/环形表、按时间分区；上传走批量 + 背压，服务端不可达时只保留最近窗口。

本地目录与存储

# /var/lib/opsagent（权限 0700，属主 opsagent） /var/lib/opsagent/ ├── agent.db # SQLite：发现结果、应用画像、策略版本、任务记录 ├── ring/ │ ├── fast/ # 5s 指标，2h │ ├── service/ # 30s 服务与端口，24h │ └── config/ # 5m 配置哈希与错误签名，24h ├── snapshots/ # 异常现场，24h / 200MB ├── packages/ # 签名技能包/工具包缓存 └── logs/ # Agent 自身日志，按大小轮转

采集器自身必须“有礼貌”：CPU 配额、IO 优先级、采集抖动、错峰、批量写入、单次读取上限；日志只读尾部与错误签名，不整文件读入内存。Agent 的资源消耗目标：空闲 CPU < 1%、常驻内存 < 100MB、磁盘写入 < 5MB/s（突发除外），并纳入验收。

不是所有数据都值得上传。服务端要的是“异常窗口 + 证据 + 趋势摘要”。把 5s 全量指标持续回传，既浪费带宽，也会把平台变成另一个时序数据库。
05
Boundaries

自巡航能做什么，
不能做什么，要写进执行器

边界不是一份“注意事项”，而是动作注册表 + 策略 + 审批。Agent 在自巡航状态只读；R2/R3 动作必须由服务端签名指令触发，且本地 CLI 不能自我批准。

默认允许 · 只读自巡航

  • 读取主机/OS/服务/端口/进程/容器元数据
  • 读取配置路径、格式、哈希；读取脱敏后的配置片段
  • 读取日志尾部、错误签名、轮转状态
  • 采集指标、生成快照、本地趋势分析
  • 执行只读诊断：连接检查、端口检查、线程栈、GC/堆摘要
  • 本地 CLI 问答、解释、生成排障报告
  • 从服务端拉取签名策略/技能包/工具包

默认禁止 · 必须审批或不做

  • 启动/停止/重启服务、kill 进程
  • 修改配置、写入应用目录、删除文件
  • 安装/卸载软件包、修改内核参数、防火墙
  • 读取密钥、私钥、密码、完整环境变量值
  • 任意 Shell、任意脚本、任意文件读取
  • 端口扫描、网络探测、横向访问其他主机
  • 把主机文件/日志原文外传到非授权地址

动作分级

级别例子执行条件审计
R0 只读status、metrics、log tail、config read（脱敏）、port check本地策略允许即可记录动作、参数哈希、结果摘要
R1 低危生成诊断包、采集线程栈、触发一次快照本地策略 + 服务端任务记录任务 ID 与产物
R2 高危重启服务、清理临时文件、切换日志级别服务端签名指令 + 人工审批 + 回滚点全程审计 + 结果回执
R3 禁止/受控部署应用、升级版本、改配置、扩缩容未来能力；变更单 + 维护窗口 + 双人审批变更单 + 逐步回滚

CLI：像 Claude Code，但不是一个本地 root Shell

CLI 能力
本地对话 + 受控工具

opsagent chat 支持自然语言、上下文、技能包；可问“这台机器为什么 5xx”“日志里最早异常是什么”“帮我生成诊断报告”。

CLI 不能
绕过服务端审批

CLI 只能发起请求；R2+ 由服务端策略与审批决定。本地用户不能自己点“同意”就把生产服务重启。

06
Security

不能伪造的指令，
不能冒充的数据

服务器 Agent 是“能执行动作的软件”，安全模型必须假设：网络可被劫持、服务端可能被攻破、Agent 证书可能泄露、本机用户可能恶意、日志内容可能提示注入。每一层都要有独立校验。

接入与身份

01

一次性加入令牌

安装包携带短 TTL、单次使用的 join token；绑定租户、预期网段/标签、可选主机名。令牌泄露不能无限注册。

02

CSR + 设备证书

Agent 生成密钥对（优先 OS keystore/TPM），提交 CSR；服务端 CA 签发带 host_id、tenant_id 的客户端证书。

03

自动/人工纳管

满足网段 + 标签 + 镜像签名策略可自动批准；否则进入待审批。未知主机默认隔离，不能执行任务。

04

证书轮换与吊销

短周期轮换；主机隔离、重装、离职/下线即吊销；Gateway 维护 CRL/OCSP 等价状态。

指令信封：LLM 永远不直接生成 Shell

{ "command_id": "cmd_01J9...", "tenant_id": "t-1001", "host_id": "host_8f2a", "action_id": "diag.thread_dump", "params": { "pid": 1842, "max_bytes": 1048576 }, "policy_version": "pol_2041", "issued_at": "2026-11-03T14:52:31+08:00", "expires_at": "2026-11-03T14:57:31+08:00", "nonce": "b7f2...", "signature": "ed25519:..." }
攻击/风险防线
伪造服务端下发命令mTLS 双向认证 + 指令签名（KMS/HSM 托管密钥）+ 动作 ID 白名单；Agent 不解析自由文本命令
重放旧命令nonce + 短过期时间 + 本机持久化 replay cache + command_id 幂等
命令发错主机/租户证书绑定 host_id/tenant_id；指令信封再次校验；主机不匹配直接拒绝
伪造 Agent 上报数据设备私钥签名遥测批次；序列号/时间窗；Gateway 校验证书与主机归属
日志/配置提示注入日志内容只作为“不可信数据”进入模型；工具调用走策略引擎，模型不能直接产生可执行命令
Agent 密钥泄露短周期证书、设备隔离、异常行为检测、吊销；高风险动作要求二次签名/审批
本机恶意用户CLI 走本地 Unix socket + peer 凭证；不以 root 运行；R2+ 仍需服务端审批
供应链/升级包二进制与技能包签名、校验和、版本固定、灰度、回滚；禁止未签名插件
LLM 不是信任边界。总控智能体可以“提议”排障动作，但最终下发必须经过策略引擎、RBAC、审批和签名。模型输出永远不能拼成 Shell 字符串直接执行。

LLM 路径与数据边界

Agent 不持有模型厂商密钥。CLI/诊断需要模型时，通过 mTLS 调服务端 LLM Gateway；服务端做租户配额、脱敏、审计和模型路由。主机侧只发送必要的上下文摘要，默认不把整份日志/配置上传。离线时 CLI 退化为本地规则与已缓存知识。

07
Closed loop

异常上报只是开始，
排障是一条可审计的闭环

Agent 本地先做一层“是否真的异常”的判断，服务端再做跨主机/跨工具关联；总控智能体下发的是诊断任务，不是“你去修”。修复永远在审批之后。

01

本地检测

阈值、基线偏离、连续次数、错误签名突增；本地聚合，避免单点抖动直接触发告警风暴。

02

带证据上报

异常事件包含：指标窗口、服务/端口、配置哈希、日志签名、最近变更、所属应用/数据中心、快照引用。

03

服务端关联

总控智能体同时查主机 Agent、Prometheus/Zabbix、ClickHouse、数据库插件、变更记录和知识库。

04

下发诊断任务

只读动作：线程栈、连接详情、日志尾部、GC 摘要、依赖端口检查、配置片段。任务带预算与超时。

05

本地分析 + 回传

Agent 在本机做初步归因，返回证据 + 结论 + 置信度；服务端保留原始证据引用，不只看模型总结。

06

修复/接管

R2+ 进入审批；R3 走变更单。人可以随时接管；Agent 不自动执行破坏性动作。

诊断动作注册表（节选）

action_id用途风险限制
diag.snapshot采集当前系统/应用快照R0只读；最大 50MB；脱敏

08
Server side

自动纳管，
但不自动信任

服务端要能自动发现新装 Agent、建立连接、分配租户、拉取清单，并在异常时调度诊断。但“自动纳管”不等于“自动放权”：未知主机先隔离，策略通过后才进入稳态。

服务端新增模块

Gateway
Agent Gateway

mTLS 长连接、心跳、遥测接收、指令下发、背压、断线重连。

Identity
Enrollment / CA

加入令牌、CSR、证书生命周期、主机隔离、吊销。

Inventory
Agent Registry / CMDB

主机、应用、服务、数据中心、版本、状态、标签。

Policy
Policy / Skills

能力包、工具包、动作白名单、采集策略、签名与灰度。

Control
总控智能体

异常关联、诊断编排、工具插件调度、结论与工单。

Audit
Command / Evidence

指令、结果、证据、审批、回滚全链路审计。

主机 → 应用系统 → 数据中心

纳管时用 IP、网段、主机名、Agent 标签、CMDB 记录做匹配；匹配结果写入主机档案，并同步到 Agent 本地知识。多候选/冲突保留，不静默覆盖。应用画像由发现结果与服务端 CMDB 合并，后续排障时可直接回答“这台机器属于哪个应用、哪个数据中心、上下游是谁”。

Agent 类型：OS 先行，其余作为插件预留

Agent 类型部署位置核心能力阶段
OS AgentLinux 服务器 / VM 内系统发现、应用识别、常驻采集、CLI、受控诊断本期主线
Virtualization AgentvCenter / KVM / 云平台宿主机、虚拟机、集群、迁移、容量预留插件
Storage Agent存储阵列 / 分布式存储池、卷、LUN、IO 延迟、容量、告警预留插件
Network Agent交换机 / 防火墙 / SDN接口、路由、ACL、会话、丢包、配置漂移预留插件

四类 Agent 共用同一套注册、策略、指令、审计协议；差异在“采集器 + 动作注册表”。不把 OS Agent 做成万能代理，也不让每类设备各造一套控制面。

09
Implementation

Go 单二进制，
小依赖、可审计、可收敛

选择 Go 的原因不是“流行”，而是静态编译、跨平台交叉编译、低运行时依赖、并发采集与 gRPC 生态成熟。目标是一台主机一个二进制 + 一个 systemd unit + 一个本地库。

Binary
opsagentd + opsagent

守护进程与 CLI 同一仓库、同一版本；CLI 通过本地 Unix socket 调守护进程，不直接持有权限。

Transport
gRPC / HTTP2 + mTLS

Agent 主动出站；双向流用于指令/心跳，批量遥测走独立流；protobuf 固定 schema。

Store
SQLite（无 cgo）+ ring

发现结果、应用画像、策略版本、任务、快照索引；高频指标用环形文件/分区表，zstd 压缩。

OS integration
systemd + /proc + journald

Linux first；包管理 dpkg/rpm；容器只读元数据；不加载内核模块，不依赖 eBPF。

进程与权限模型

# systemd hardening 方向（示意） User=opsagent Group=opsagent NoNewPrivileges=true ProtectSystem=strict ProtectHome=true PrivateTmp=true ReadOnlyPaths=/proc /sys /etc /var/log ReadWritePaths=/var/lib/opsagent CapabilityBoundingSet= RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6 CPUQuota=50% MemoryMax=256M IOWeight=50

默认不以 root 运行。需要读取 journald/系统服务时，通过组成员或只读路径授权；不为“方便”开放 docker socket、宿主 root shell 或任意文件读。若某个采集必须更高权限，拆成最小 helper，并单独审计。

代码结构（建议）

模块职责关键约束
cmd/opsagentd守护进程入口、systemd notify、生命周期不包含业务逻辑
cmd/opsagentCLI、交互式对话、诊断命令通过 Unix socket 调 daemon

10
Expansion

未来能力：
部署、升级、更多设备类型

能力扩展不改变安全模型。新增动作仍然要注册、分级、签名、审批、可回滚；只是把“执行器”从只读诊断扩展到变更执行。

应用部署/升级蓝图

01

变更单

应用、版本、目标主机、维护窗口、回滚版本、审批人；与现有 ITSM/变更管理对接。

02

预检

磁盘、依赖、端口、配置兼容、当前健康；预检失败不进入执行。

03

灰度/分批

先 1 台 canary，观察健康与错误率；再按批次滚动，失败自动暂停。

04

执行与回滚

签名制品、校验和、原子替换、健康检查；失败回滚到上一版本，保留现场。

05

验收与知识

验证端口/日志/指标；变更记录进入知识库；失败样本进入复盘。

R3 的门槛：部署/升级不是“给 Agent 一个 Shell”。它需要制品签名、变更审批、维护窗口、双人复核、回滚演练和审计；没有这些，不做。

Agent 类型插件化

虚拟化、存储、网络 Agent 作为服务端插件接入：统一注册、证书、指令、审计；各自提供采集器与动作注册表，不共享 OS Agent 的 root 权限。设备侧 Agent 只做“该设备允许的只读/受控动作”，不做跨域横向。

11
Roadmap

P1.6 之后，
独立 16 周主线

Server Agent 是新的、跨平台、强安全属性的主线。建议不塞进 P1/P1.5/P1.6 的 28 周，而是在 P1.6 之后作为 P2-A/P2-B 独立推进；如果要并行，需要额外 2.5 FTE，且会拉长联调与安全评审。

P2-A · 10 周

可用 Agent

Linux 单二进制、注册/证书、受控发现、应用画像、常驻采集、异常上报、CLI 只读对话、服务端 Gateway/Registry。

P2-B · 6 周

可排障 Agent

签名诊断指令、线程栈/日志/连接/配置检查、证据回传、总控智能体编排、本地知识、安全加固与灰度。

P3 · 未来

可变更 Agent

应用部署/升级、虚拟化/存储/网络 Agent 插件、跨设备协同、变更审批与回滚。

Track A
主机侧

Go daemon、CLI、发现、采集、策略、执行器、本地知识。

Track B
服务端

Gateway、CA、Registry、命令总线、总控智能体、工具插件。

Track C
安全/质量

威胁建模、证书/签名、伪造/重放测试、隔离、资源验收。

Decisions

需要确认的
六个实现边界

这些不是“功能要不要”，而是“第一版按什么安全/运维边界落地”。确认后才能进入 Agent 任务级计划。

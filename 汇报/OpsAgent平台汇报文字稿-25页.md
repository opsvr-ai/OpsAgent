## 01 封面

**标题：**

> 从告警到根因：  
> 让操作系统智能体成为可调度的运维现场

**副标题：**

> OpsAgent 多租户 AIOps 平台设计汇报

**一句话：**

> 不是在监控面板上再加一个 AI 对话框，而是把服务器现场、智能体调度、证据链和故障定界做成一套可运行、可审计、可演进的系统。

**建议视觉：**

左侧一台服务器，右侧一个平台控制面，中间是 Agent 出站连接；不要放通用 AI 机器人插画。

## 02 执行摘要：一页讲清平台

**五个判断：**

1. 运维不缺告警，缺的是从告警到根因的可信路径。
2. 单机智能体只能看见本机，跨节点定界必须由平台总调度完成。
3. 故障定界的关键不是“让模型猜”，而是“先定界、再定因、用证据验证”。
4. 拓扑不应该靠人工维护，应该由 Agent 采集的真实连接自动生成。
5. 当前平台已经具备 Agent 现场能力 + 故障定界原型；下一步是把原型工程化为可规模化产品。

**汇报结论：**

> 平台已经走通“Agent 发现 → 平台聚合 → 总调度 → Agent 补采 → 根因收敛”的闭环原型，接下来重点是把故障定界从能跑，做到可解释、可规模化、可运营。

## 03 背景：告警很多，但根因很少

**现象：**

```text
CPU 高
内存高
数据库连接拒绝
应用接口超时
端口不可达
```

这些可能只是**结果**，不是**原因**。

**三个断裂：**

1. 数据断裂：主机、应用、数据库、网络数据分散。
2. 协作断裂：值班人员在不同系统之间手工拼证据。
3. 经验断裂：老师傅知道怎么查，但经验没有沉淀成系统。

**结论：**

> 运维智能体需要同时具备两种能力：  
> 主机现场的采集能力，平台侧的组织和定界能力。

---

## 04 平台定位：不是监控面板，而是智能体控制平面

**四层定位：**

| 层次 | 职责 |
| --- | --- |
| 控制面 | 租户、身份、权限、模型、审批、审计、应用系统 |
| 运行时 | 会话、规划、工具调用、证据汇总、总调度 |
| 现场执行 | 操作系统智能体，在本机发现、采集、巡检、诊断 |
| 数据与知识 | 资产、事件、连接、指标、技能、历史案例 |

**平台边界：**

> 模型负责理解、规划和总结；  
> 平台负责权限、命令、证据和审计；  
> 操作系统智能体负责本机事实采集和受控动作。

---

## 05 设计理念：五条原则

### 原则一：现场事实优先

根因必须能落到进程、端口、连接、日志、指标和拓扑事实。

### 原则二：先定界，再定因

先判断影响范围，再判断根因位置，避免把下游症状当上游原因。

### 原则三：平台编排优先于单点智能

Agent 提供现场细节，平台提供跨节点视角。

### 原则四：只读自动，写操作审批

日常检查不打断人；有风险动作必须走平台审批。

### 原则五：每次故障都要沉淀

一次排障不只是解决问题，还要沉淀技能、规则、证据模板和案例。

## 06 总体架构：控制面、运行时、现场执行

```text
Web / CLI
  │
控制面
  ├─ 租户 / 权限 / 审计
  ├─ 应用系统 / 资产 / 事件
  ├─ 模型 / 技能 / 审批
  └─ 故障定界 / 事件指挥
  │
智能体运行时
  ├─ 会话 / 规划
  ├─ 工具 / 总调度
  └─ 证据汇总
  │
操作系统智能体网络
  ├─ 发现 / 上报
  ├─ 巡航 / 巡检
  ├─ 本机诊断
  └─ 受控执行
  │
主机 / 进程 / 端口 / 连接 / 日志
```

**关键设计：**

- 平台不把数据库凭据下发给 Agent。
- Agent 不开放入站端口。
- 平台与 Agent 之间使用身份校验和签名命令。
- 模型只通过平台模型网关访问。

## 07 端到端工作流：从异常到结论

```text
01 Agent 发现异常
02 平台归并事件
03 汇总应用系统
04 生成访问拓扑
05 计算故障边界
06 判断证据缺口
07 调度 Agent 补采
08 总调度二次决策
09 输出根因/影响/建议
10 进入事件、审批、复盘
```

**核心变化：**

> 从“告警列表 + 人工排查”  
> 变成“故障案例 + 自动补采 + 证据收敛”。

## 08 操作系统智能体：服务器上的受控操作员

**定位：**

> 不是远程 Shell，而是部署在每台服务器上的受控运维代理。

**已实现能力：**

- Go 单二进制
- 注册与心跳
- 资产发现
- 指标采集
- 重要对象巡检
- 异常上报
- 本机只读诊断
- 技能执行
- 结果回传

**不做的事情：**

- 不开放入站端口
- 不执行任意 Shell
- 不把模型密钥放在主机
- 不在本地批准高风险操作


**原则：**

> Agent 回传的是“可用于定界的结构化事实”，不是整段原始日志。

**能力扩展：**

- 内置技能自动同步到平台
- 平台可以创建自定义技能
- 技能可下发到全部在线、指定应用系统或指定主机

**本机记忆：**

- 最近检查记录

- 检查点

**价值：**

> Agent 不是一个“每次从零开始”的命令执行器，  
> 而是带有本机上下文和历史记忆的现场智能体。

## 14 安全模型：能采集，但不能乱来

**四个约束：**

1. **网络方向**
   - 只主动出站
   - 不开放入站端口

2. **动作分级**
   - 只读检查自动执行
   - 有风险动作走平台审批
   - 高风险动作拒绝或变更单

3. **执行方式**
   - 平台下发结构化动作
   - Agent 侧动作注册表
   - 参数和路径受约束

4. **可追溯**
   - 命令、结果、审批、异常全部落库
   - 本机也有审计

**一句话：**

> 给智能体“看”的能力，谨慎给“动”的能力。

## 15 智能体控制：从会话到批量调度

**已实现：**

- 在智能体会话中直接下发指令
- 指定单台 Agent
- 指定应用系统
- 全部在线主机
- 批量执行只读检查
- 汇总结果
- 重试失败节点

**写操作：**

- 不在普通对话中直接执行
- 进入平台审批
- 审批通过后才下发

**管理价值：**

> 把“登录很多台机器检查”变成“一次调度，多机返回，平台汇总”。

## 16 故障定界：重新定义问题

**传统排障：**

```text
看告警 → 猜原因 → 登录机器 → 查日志 → 再猜
```

**故障定界：**

```text
异常聚合
  → 故障边界
  → 根因候选
  → 自动补采
  → 证据收敛
  → 结论
```

**两个问题分开回答：**

| 问题 | 输出 |
| --- | --- |
| 影响了哪些节点、应用、端口和依赖？ | 故障边界 |
| 根因最可能在哪？ | 根因候选 |
| 证据是否支持？ | 置信度和证据链 |

---

## 17 为什么传统根因分析效果不好

**四个原因：**

1. **只有单点数据**
   - 只看一台主机，看不见上下游。

2. **只有告警文本**
   - 没有进程、端口、连接和日志事实。

3. **没有时间序列**
   - 不知道异常是先发生还是后发生。

4. **模型没有约束**
   - 没有证据引用、没有候选评分，容易给出“听起来对”的答案。

**结论：**

> 根因分析的质量，取决于输入的事实质量，而不是模型参数大小。

## 18 故障定界流程

```text
01 信号归一化
02 按应用系统 + 时间窗口聚合
03 构建访问拓扑
04 识别异常节点
05 计算故障边界
06 生成根因候选
07 判断证据缺口
08 自动调度 Agent 补采
09 合并证据重新评分
10 总调度输出结论
```

**实现状态：**

- 已实现：自动触发、应用系统汇总、模型分析、自动补采、证据步骤、拓扑上下文、页面呈现。
- 工程化中：时间窗口聚合、指标基线、边界传播算法、候选评分、证据引用校验。

## 19 信号聚合：不是每条告警都开一个分析

**目标：**

```text
应用系统 + 10 分钟窗口 + 主异常指纹
  → 一个 Fault Case
```

**聚合原则：**

- 同应用系统同指纹异常合并。
- 拓扑上下游关联异常合并。
- 重复事件去重。
- 已关闭 Case 后再次出现，新建 Case 并关联历史。

**为什么重要：**

> 领导看到的应该是一个“故障案例”，  
> 而不是 200 条重复告警。

## 20 拓扑自动生成：访问关系不是画出来的

**Agent 采集：**

```bash
ss -tnp
```

或 `/proc/net/tcp`、`tcp6` 兜底。

**得到：**

```text
源 IP / 源端口
目标 IP / 目标端口
TCP 状态
进程信息
```

**平台映射：**

```text
源/目标 IP   → Agent 节点
源/目标端口  → 进程或服务
ESTAB 连接   → 拓扑边
```

**最终形成：**

```text
app-01
  java(order-service):48012
        │ TCP ESTAB · 312
        ▼
db-01
  mysqld:3306
```

**叠加异常：**

```text
app-01：连接池 312/300 · CPU 96%
db-01：连接拒绝 18%
app-02：错误率 8.7%
```

## 21 故障边界和根因候选

**边界计算：**

- 从异常节点出发。
- 沿连接边向下游扩散 1–2 跳。
- 标记根因候选区、受影响区、边界外依赖。

**根因候选评分维度：**

```text
时间优先性
拓扑上游性
异常严重度
重要资产权重
持续性
下游扩散惩罚
```

**输出：**

```text
Top 3 根因候选
每个候选带证据、评分和缺口
```

**核心原则：**

> 先给候选，不急着给唯一答案。

## 22 智能体协同：总调度如何调度 Agent

```text
总调度发现问题
  → 判断证据缺口
  → 生成受控采集任务
  → 平台下发给目标 Agent
  → Agent 本机执行
  → 返回结构化证据
  → 平台写入 Case
  → 总调度更新候选和边界
  → 证据足够，输出结论
```

**任务约束：**

- 目标必须在当前应用系统。
- 只允许受控 probe 类型。
- 单次分析有数量、并发、超时预算。
- 重复任务去重。
- 结果进入证据链。

**一句话：**

> 总调度负责“问对问题”，  
> Agent 负责“拿到本机事实”，  
> 平台负责“把事实变成可追溯的结论”。

---

## 23 结论与证据：让模型可解释

**平台给模型四类输入：**

1. 应用系统节点和指标
2. 归一化异常事件
3. 自动生成的访问拓扑
4. Agent 补采返回的结构化证据

**模型输出：**

```json
{
  "rootCause": "order-service 连接池耗尽",
  "confidence": 0.82,
  "findings": [],
  "followUp": []
}
```

**平台约束：**

- 结构化输出
- 结论落库
- 低置信度标记人工确认
- 结论逐步要求引用证据
- 模型不可用时规则引擎兜底

## 24 案例：订单中心数据库连接异常

> 机制演示案例，数据为示意，链路已在本地原型验证。

### 现象

```text
订单提交超时
MySQL 连接拒绝
app-01 CPU 96%
```

### 总调度第一次判断

```text
候选一：order-service 连接池耗尽
候选二：MySQL 连接数达到上限
候选三：app-01 CPU 饱和
```

### 自动调度

```text
app-01：进程树 / 线程 / 日志 / netstat
db-01：3306 / 连接数 / 慢查询 / netstat
app-02：错误率 / 连接 / 日志
```

### Agent 返回

```text
app-01：
  312 个线程
  HikariPool 连接超时 17 次
  1,842 条 ESTAB，38 条跨节点边

db-01：
  3306 正常监听
  连接 1204 / 1500
  未达到 max_connections

app-02：
  错误率 8.7%
  连接池使用率 61%
```

### 二次决策

```text
order-service 连接池候选：0.64 → 0.82
MySQL 连接数候选：0.61 → 0.34
app-02：从候选根因降为受影响节点
```

### 最终结论

```text
根因：app-01 order-service 连接池耗尽
影响：app-02、db-01
边界外：短信网关
置信度：82%
```

## 25 价值、当前进展与愿景

### 已落地能力

- 多租户控制台
- Agent 注册、心跳、发现、资产上报
- 服务、进程、端口、运维工具、连接采集
- 重要对象标记与 30 秒巡航
- 异常事件上报
- 会话控制单台 / 应用系统 / 全部在线 Agent
- 技能管理和下发
- 故障定界原型：自动触发、汇总、调度、补采、结论
- 访问关系拓扑上下文
- 故障定界页面：工作台、详情、过程、Agent 协作

### 价值

- 值班人员：从多系统手工拼证据，变成平台自动组织证据。
- 运维团队：从个人经验，变成可复用技能和案例。
- 管理者：故障影响范围和结论可追踪、可复盘。
- 平台：每次故障都沉淀为下一次定界的数据资产。

### 未来愿景

**阶段一：把现场做扎实**

- Agent 覆盖率
- 资产和连接准确性
- 巡检和告警质量

**阶段二：把定界做可信**

- 指标时间序列
- Case 聚合和去重
- 故障边界算法
- 根因候选评分
- 受控补采和证据引用

**阶段三：把闭环做完整**

- 事件指挥 / 审批 / 知识联动
- 网络、存储、虚拟化 Agent
- 多智能体协同
- 自愈和变更建议

### 结束语

> 我们做的不是一个“会回答问题的 AI”，  
> 而是一套“能在真实运维现场组织事实、调度智能体、收敛根因”的系统。

## 视觉与动效设计说明（HTML PPT 制作依据）

### 一、整体视觉基调

- **全浅色**：暖白/冷白背景，白色内容卡片，深墨色文字。
- **主色**：一种工程蓝，避免多主色竞争。
- **异常色**：克制的砖红 / 琥珀，只用于异常、根因候选和边界。
- **技术感来源**：细线、编号、网格、留白、层级、数据流动，而不是深色背景和发光。
- **每页只保留一个视觉焦点**：要么是一张架构图，要么是一张拓扑图，要么是一条流程图。

### 二、动效原则

1. **动效服务于解释**
   - 每段动画都必须回答“谁在动、为什么动、动完说明什么”。
   - 不做无意义的粒子、漂浮和循环装饰。

2. **先结构，后数据**
   - 先出现层级/节点，再出现连线，最后出现数据流和结论。

3. **一次只讲一件事**
   - 同一时间最多一个主动画。
   - 其他元素静止或低对比，不抢焦点。

4. **可回放、可跳过**
   - 每页提供“重播”按钮。
   - 支持空格暂停、方向键翻页。
   - `prefers-reduced-motion` 下自动降级为静态图。

5. **性能约束**
   - 只对 `transform`、`opacity`、`stroke-dashoffset` 做动画。
   - 不触发布局抖动。
   - 单页动画总时长控制在 6–12 秒。

### 三、平台架构图动效

**画面结构：**

```text
Web / CLI
   ↓
控制面
   ├─ 租户 / 权限 / 审计
   ├─ 应用系统 / 资产 / 事件
   ├─ 模型 / 技能 / 审批
   └─ 故障定界
   ↓
智能体运行时（规划 / 工具 / 总调度）
   ↓
操作系统智能体网络
   ↓
主机 / 进程 / 端口 / 连接 / 日志
```

**动画顺序：**

1. 底层主机节点先出现。
2. 操作系统智能体节点出现，向上发出心跳光点。
3. 智能体运行时出现，控制面逐层展开。
4. 控制面与运行时之间出现双向数据流。
5. 顶部 Web/CLI 出现。
6. 最后高亮“故障定界”和“总调度”两个核心节点。

**数据流方向：**

```text
向上：心跳、资产、事件、证据
向下：策略、任务、命令、审批
```

### 四、访问拓扑图动效

**画面结构：**

```text
app-01
  java(order-service):48012
        │ TCP ESTAB · 312
        ▼
db-01
  mysqld:3306
```

**动画顺序：**

1. 主机节点逐个出现。
2. 节点内部展开进程/服务徽标和端口。
3. 连接边从源节点向目标节点绘制，线条使用 `stroke-dashoffset` 生长。
4. 边上依次出现协议、端口、ESTAB 数量。
5. 异常节点出现红色/琥珀色光晕。
6. 根因候选区先亮起。
7. 受影响区沿拓扑向下游扩散。
8. 边界外节点变灰，并显示“边界外”。
9. 最终停留 2 秒，让观众看清结论。

**必须表达清楚的三个层次：**

```text
哪个节点
哪个进程/服务
访问了哪个节点的哪个端口
```

### 五、“动态工作原理”主视觉

建议在 06 或 18 页做一个 **12 秒循环动画**：

```text
第一幕：发现
  异常信号从主机出现 → 汇聚到平台

第二幕：调度
  总调度拆解证据缺口 → 任务飞向不同 Agent

第三幕：收敛
  Agent 返回证据 → 拓扑边形成 → 边界扩散 → 根因候选收敛
```

**交互：**

- 自动播放。
- 空格暂停。
- 点击“分步”逐幕播放。
- 点击“重播”从头开始。

### 七、实现方式建议

- **单文件 HTML**：CSS、SVG、JS 全部内联，平台内可直接打开。
- **动画引擎**：优先使用 Web Animations API 和 CSS transitions，不依赖外部 CDN。
- **SVG 连线生长**：`stroke-dasharray` + `stroke-dashoffset`。
- **节点出现**：`opacity + transform: translateY/scale`。
- **数据流**：沿路径移动的小圆点或渐变高亮，不用大量粒子。
- **场景控制**：每页一个 `data-scene`，用统一时间线控制器播放。
- **翻页**：键盘 `←/→`、空格、点击页码；顶部显示进度。
- **降级**：`prefers-reduced-motion` 时直接显示最终态。
- **可维护**：把节点、边、文案放到一个页面配置对象中，避免每页重复写动画逻辑。

### 八、动效禁区

- 不做 3D 旋转地球。
- 不做大面积粒子背景。
- 不做霓虹发光。
- 不做无意义循环漂浮。
- 不让动画遮挡文字。
- 不让动画延迟用户翻页。

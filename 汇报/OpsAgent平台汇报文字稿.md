## 01 封面

**标题：从告警到根因，让操作系统智能体成为可调度的运维现场**

**副标题：OpsAgent 多租户 AIOps 平台设计汇报**

**一句话：**

> 不是在监控面板上再加一个 AI 对话框，而是把操作系统现场、智能体调度、证据链和故障定界做成一套可运行、可审计、可复用的运维系统。

**讲述重点：**

- 平台的核心不是“会聊天”，而是“能发现、能调度、能取证、能收敛、能闭环”。

## 02 背景：运维真正缺的不是告警，而是从告警到根因的路径

**核心观点：**

今天的运维现场通常不缺监控，缺的是把分散信号变成可执行结论的能力。

**三个现实问题：**

1. **告警碎片化**
   - 主机、进程、端口、日志、应用指标分散在不同系统。
   - 同一个故障会在多个系统重复告警，值班人员先被淹没。

2. **根因依赖个人经验**
   - 看到 CPU 高，不等于 CPU 是根因。
   - 看到数据库连接拒绝，不等于数据库是根因。
   - 真正的根因往往在“上游应用的连接池、最近变更、异常进程、端口关系”里。

3. **通用 AI 缺少现场事实**
   - 只把告警文本交给大模型，模型只能猜。
   - 没有进程、端口、连接、日志、指标、拓扑，就没有可验证的根因。

**结论：**

> 运维智能体必须同时具备两种能力：  
> **在主机现场采集事实的能力**，以及**在平台侧做跨节点定界和调度的能力**。

**建议视觉：**

左侧“告警很多”，中间“信息断裂”，右侧“人工经验”，最终汇成一句话：缺少一条可信的定界链路。

## 03 平台定位：OpsAgent 是运维智能体的控制平面

**核心观点：**

OpsAgent 不是又一个监控面板，而是把“看见、判断、派工、执行、复盘”收进一个平台。

**四个层次：**

| 层次 | 作用 |
| --- | --- |
| 控制面 | 租户、用户、角色、模型、审批、审计、应用系统、技能 |
| 运行时 | 智能体会话、规划、工具调用、证据汇总 |
| 现场执行 | 操作系统智能体，在本机采集、巡检、诊断 |
| 数据与知识 | 指标、事件、资产、连接、技能、历史记录 |

**平台边界：**

- 平台不把模型当成执行器。
- 模型负责理解、规划和总结。
- 平台负责权限、审批、命令、证据和审计。
- 操作系统智能体负责本机事实采集和受控动作。

**一句话：**

> 模型可以提出假设，但不能绕过平台直接操作主机。

## 04 设计理念：五条原则决定平台走向

### 原则一：现场事实优先于模型推测

根因必须建立在进程、端口、连接、日志、指标和拓扑事实之上。

### 原则二：先定界，再定因

先判断“影响了哪些节点、应用、端口和依赖”，再判断“根因是哪一个”。  
不是让模型看一眼告警就直接给结论。

### 原则三：平台编排优先于单点智能

单台主机上的 Agent 很聪明，但它只看见本机。  
跨主机的上下游关系、故障扩散和根因收敛，必须由平台总调度完成。

### 原则四：默认不信任，最小权限

- 操作系统智能体默认只做只读采集。
- 写操作必须走平台审批。
- 智能体不开放入站端口。
- 所有命令、返回、审批和结论可审计。

### 原则五：每一次故障都要沉淀为能力

一次排障不应该只解决一次问题。  
技能、证据模板、拓扑规则和故障案例都应该可复用。

**建议视觉：**

五条原则做成纵向编号卡片，最后落到一句话：

> 事实驱动、边界先行、平台编排、最小权限、持续沉淀。

## 05 总体架构：控制面、运行时、现场执行三层协同

```text
┌──────────────────────────────────────────────┐
│                   Web / CLI                   │
│        工作台 · 智能体会话 · 故障定界          │
├──────────────────────────────────────────────┤
│                平台控制面                      │
│  租户与权限 · 应用系统 · 模型 · 审批 · 审计     │
│  事件中心 · 故障定界 · 技能 · 资产 · 知识       │
├──────────────────────────────────────────────┤
│                智能体运行时                     │
│  会话 · 规划 · 工具调用 · 证据汇总 · 总调度     │
├──────────────────────────────────────────────┤
│           操作系统智能体网络                    │
│  发现 · 上报 · 巡航 · 诊断 · 受控执行           │
├──────────────────────────────────────────────┤
│        主机 / 进程 / 端口 / 连接 / 日志         │
└──────────────────────────────────────────────┘
```

**三层关系：**

- **控制面**：定义“谁能做什么、在哪个应用系统做、是否需要审批”。
- **运行时**：把问题拆成计划，把计划变成工具调用，把结果变成证据和结论。
- **操作系统智能体**：把“本机发生了什么”变成结构化事实，回传平台。

**关键点：**

> 智能体不是替代平台，而是平台的“现场手脚”；平台不是替代智能体，而是智能体的“指挥系统”。

## 06 端到端工作流：从异常到结论的完整闭环

```text
01 发现
  Agent 事件 / 指标越阈 / 重要对象缺失
        ↓
02 聚合
  按应用系统 + 时间窗口 + 指纹归并
        ↓
03 建 Case
  生成故障定界案例，收敛重复告警
        ↓
04 构建拓扑
  节点、进程、服务、端口、访问关系
        ↓
05 计算边界
  根因候选区 / 受影响区 / 边界外依赖
        ↓
06 自动补采
  按证据缺口调度对应操作系统智能体
        ↓
07 二次决策
  排除错误候选，更新边界和根因评分
        ↓
08 最终结论
  根因、影响范围、证据、置信度、处置建议
        ↓
09 闭环
  创建事件 / 审批 / 复盘 / 沉淀知识
```

**讲述重点：**

- 这条链路里，模型不是唯一主角。
- 平台负责“组织事实”，智能体负责“采集事实”，模型负责“解释事实”。
- 每一步都有输入、输出和责任人。

## 07 操作系统智能体：服务器上的受控操作员

**核心观点：**

> 操作系统智能体不是远程 Shell，而是部署在每台服务器上的受控运维代理。

**它做什么：**

1. 注册与心跳
2. 资产发现
3. 指标采集
4. 重要对象巡检
5. 异常上报
6. 按平台指令做本机诊断
7. 返回结构化证据
8. 在授权范围内执行动作

**它不做什么：**

- 不开放入站端口。
- 不执行任意 Shell。
- 不把模型密钥放到主机。
- 不在本机直接批准高风险操作。
- 不把整段原始日志无差别回传。

**技术形态：**

- Go 单二进制。
- 主动出站注册与心跳。
- 平台下发结构化命令。
- 本机执行技能和只读检查。
- 结果回传控制面。

**建议视觉：**

一张“服务器内部的 Agent 小方块”图：

```text
主机
├── 进程 / 端口 / 服务
├── 日志 / 指标 / 连接
├── Agent
│   ├── 发现
│   ├── 采集
│   ├── 巡护
│   └── 证据
└── 平台 ← 出站心跳 / 命令 / 证据
```

## 08 操作系统智能体工作原理：注册、发现、巡航、取证

### 8.1 注册与身份

- Agent 首次启动向平台注册。
- 平台记录租户、主机、应用系统、版本、能力。
- 后续心跳携带状态、指标、发现结果。
- 命令必须带 Agent 身份和平台签名。

### 8.2 首次发现和持续发现

Agent 发现：

```text
操作系统信息
服务
应用进程
监听端口
运维工具
应用部署路径
配置和日志位置
访问连接
```

这些结果形成：

```text
agent_inventory         资产与巡检对象
agent_connections       本机 ESTAB 连接
agent_events            异常信号
```

### 8.3 重要对象巡检

平台可以对资产标记：

```text
重要 + 监控
```

标记后进入该 Agent 的 watchlist：

```text
重要进程未运行
重要端口未监听
重要服务未运行
```

### 8.4 30 秒级自主巡航

- 平台配置最低 30 秒巡航间隔。
- Agent 每次检查：
  - 磁盘可用率
  - 内存使用率
  - 1 分钟负载
  - 重要进程
  - 重要端口
  - 重要服务
- 异常写入事件并上报。

### 8.5 按需诊断

平台或会话下发检查任务，例如：

```text
检查 Java 进程、3306 端口和最近日志
```

Agent 在本机执行只读检查并返回：

```text
进程树
端口状态
服务状态
最近日志
网络连接
磁盘和内存
```

### 8.6 技能、记忆、会话

Agent 本机保留：

```text
/opt/opsagent/
├── skills/        SKILL.md
├── state/         memory / sessions / checkpoints
├── snapshots/     巡航和配置快照
├── audit/         本地操作审计
└── logs/          Agent 日志
```

这样 Agent 不是一个“每次从零开始”的命令执行器，而是带有本机上下文和历史记忆的现场智能体。

**讲述重点：**

> 平台看到的是“跨主机视角”，Agent 看到的是“本机真实细节”。  
> 故障定界的质量，取决于这两者能否拼在一起。

## 09 操作系统智能体的安全模型：能采集，但不能乱来

**四个约束：**

1. **网络方向**
   - Agent 只主动出站。
   - 不开放监听端口。

2. **动作分级**
   - 只读检查自动执行。
   - 有风险动作平台审批。
   - 高风险动作拒绝或变更单。

3. **执行方式**
   - 平台下发结构化动作，不下发裸命令。
   - Agent 侧有动作注册表和参数约束。

4. **可追溯**
   - 命令、结果、审批、异常全部落库。
   - 本地也有审计。

**一句话：**

> 给智能体“看”的能力，谨慎给“动”的能力。

## 10 故障定界：不是猜根因，而是先确定故障边界

**核心观点：**

> 故障定界要回答两个问题：  
> **第一，影响范围到哪里？**  
> **第二，根因最可能在哪里？**

### 为什么要“定界”

一个应用异常，可能是：

- 自身进程/线程/连接池问题
- 上游调用方超时
- 下游数据库拒绝
- 网络或端口异常
- 主机资源问题
- 最近变更

如果只看单个节点，很容易把“结果”当“原因”。

### 定界和定因的区别

| 阶段 | 回答的问题 | 输出 |
| --- | --- | --- |
| 定界 | 影响了哪些节点、应用、端口和依赖 | 故障边界 |
| 定因 | 根因在哪个节点、哪个进程/服务 | 根因候选 |
| 验证 | 证据是否支持这个根因 | 证据链和置信度 |

## 11 故障定界总体流程

```text
异常信号
  → 归一化与去重
  → 按应用系统 + 时间窗口聚合为 Fault Case
  → 构建应用访问拓扑
  → 识别异常节点
  → 计算故障边界
  → 生成根因候选
  → 判断证据缺口
  → 自动调度 Agent 补采
  → 合并证据重新评分
  → 总调度智能体输出最终结论
```

**四个关键词：**

1. **聚合**：不按每条告警分别分析
2. **拓扑**：用真实访问关系计算影响范围
3. **补采**：证据不足时再调度 Agent
4. **收敛**：总调度合并多路证据给结论

## 12 拓扑怎么来：由 Agent 的 netstat 数据自动绘制

**核心创新点：**

访问关系不是人工维护的 CMDB，也不是平台猜测，而是由操作系统智能体采集本机连接后自动生成。

### 数据采集

Agent 采集：

```bash
ss -tnp
```

以及 `/proc/net/tcp`、`/proc/net/tcp6` 作为兜底，得到：

```text
源地址 / 源端口
目标地址 / 目标端口
TCP 状态
进程信息
```

### 平台映射

```text
源/目标 IP
  → 对应 Agent 节点

源/目标端口
  → 对应进程或服务

ESTAB 连接
  → 拓扑边
```

最终形成：

```text
app-01
  java(order-service):48012
        │  TCP ESTAB · 312
        ▼
db-01
  mysqld:3306
```

并叠加：

```text
节点异常
  app-01：连接池满 / CPU 96%
  db-01：连接拒绝 18%
  app-02：错误率 8.7%
```

### 自动绘制的价值

- 不依赖人工维护调用关系。
- 反映真实运行态，而不是静态配置。
- 能直接回答：
  - 哪个节点上的哪个进程/服务
  - 访问了哪个节点上的哪个进程/服务
  - 使用什么端口
  - 哪个节点有异常
  - 哪些是边界外依赖

**一句话：**

> 拓扑不是画出来的，是操作系统智能体在每台机器上“看见”之后，由平台自动拼出来的。

## 13 智能体协同：总调度如何调度操作系统智能体

**核心原则：**

> 总调度不直接执行命令，操作系统智能体不在本机直接给最终根因。  
> 两者通过平台的任务、证据和状态协同。

### 协同流程

```text
总调度发现问题
  → 判断证据缺口
  → 生成受控采集任务
  → 平台下发给目标 Agent
  → Agent 在本机执行只读检查
  → 返回结构化证据
  → 平台写入 Case
  → 总调度更新候选和边界
  → 如果证据仍不足，继续定向补采
  → 证据足够，输出最终结论
```

### 任务长什么样

```json
{
  "probeType": "process_tree",
  "hostname": "app-01",
  "target": "java",
  "reason": "连接池候选缺少线程和日志证据",
  "priority": 1
}
```

### 平台约束

- 目标必须在当前应用系统内。
- 只允许受控探测类型。
- 单次分析有任务数量上限。
- 并发和超时有预算。
- 重复任务去重。
- 返回结果写入证据链。

### Agent 返回什么

```text
执行了哪些检查
看到的关键事实
返回的证据编号
对当前定界的支持或反证
```

例如：

```text
app-01
  采集：进程树 / 线程 / 日志 / netstat
  返回：312 个线程，HikariPool 连接超时 17 次
  贡献：order-service 候选 0.64 → 0.82
  结论：支持应用连接池根因

db-01
  采集：3306 / 连接数 / 慢查询 / netstat
  返回：3306 正常，连接 1204 / 1500
  贡献：数据库候选 0.61 → 0.34
  结论：排除数据库根因

app-02
  采集：错误率 / 连接 / 日志
  返回：错误率 8.7%，连接池 61%
  贡献：标记为受影响节点
  结论：不是第二根因
```

**一句话：**

> 总调度负责“问对问题”，操作系统智能体负责“拿到本机事实”，平台负责“把事实变成可追溯的结论”。

## 14 根因收敛：模型如何被约束

**不是让模型自由发挥，而是给模型四类输入：**

1. 应用系统节点和指标
2. 归一化异常事件
3. 自动生成的访问拓扑
4. Agent 补采返回的结构化证据

**模型输出：**

```json
{
  "rootCause": "order-service 连接池耗尽",
  "confidence": 0.82,
  "findings": [],
  "followUp": []
}
```

**平台约束：**

- 输出必须结构化。
- 结论必须落库。
- 置信度低于阈值时标记“待人工确认”。
- 后续版本要求结论引用证据编号。
- 模型不可用时，规则引擎仍能给出基础定界。

**一句话：**

> 模型不是“最终裁判”，而是“在证据约束下的分析器”。

## 15 创新点：六个真正的差异

### 创新一：操作系统智能体是“受控操作员”，不是远程 Shell

- 主动出站
- 不开放入站端口
- 动作分级
- 平台签名
- 本机审计

### 创新二：先定界，再定因

- 先算影响范围
- 再收敛根因
- 避免把下游症状当根因

### 创新三：拓扑由真实 netstat 自动生成

- 不靠人工 CMDB
- 进程/服务/端口级别
- 能显示异常节点
- 能区分边界外依赖

### 创新四：总调度 + 边缘 Agent 的混合智能

- 本机事实在 Agent
- 全局推理在平台
- 平台调度，Agent 执行
- 不让单机 Agent 承担全局判断

### 创新五：证据不足才补采

- 不是每次都把所有命令跑一遍
- 按证据缺口定向采集
- 有预算、有并发、有超时
- 补采结果反向更新根因评分

### 创新六：只读自动，写操作审批

- 日常检查不打断人
- 有风险动作走审批
- 人工 break-glass 不进模型
- 每一次动作可审计

---

## 16 平台价值：从“人找答案”到“系统组织证据”

### 对值班人员

- 不再从多个系统手工拼告警
- 先看到故障边界，再决定排查方向
- 智能体自动补采，减少来回登录主机

### 对运维团队

- 把排障经验变成技能和规则
- 把“老师傅的判断”变成可复用的证据链
- 故障过程可复盘、可审计

### 对管理者

- 故障影响范围可量化
- 处理过程可追踪
- 根因结论可解释
- 重复问题可沉淀

### 对平台

- 操作系统智能体持续提供现场事实
- 故障定界持续产生结构化案例
- 案例和技能反哺下一次定界

**建议的汇报口径：**

> 短期看，缩短故障定位时间；  
> 中期看，把排障过程标准化；  
> 长期看，把运维现场变成可持续学习的数据资产。

## 17 当前进展与阶段边界

### 已具备的基础能力

- 多租户控制台
- 操作系统智能体注册、心跳、发现
- 资产上报：服务、进程、端口、运维工具
- 重要对象标记与 30 秒巡航
- 异常事件上报
- 智能体会话控制单台/应用系统/全部在线 Agent
- 运维技能管理和下发
- 故障定界原型：自动触发、汇总、调度、补采、结论
- 访问关系数据和拓扑上下文
- 故障定界页面：工作台、详情、定界过程、Agent 协作

### 需要继续强化的方向

- 指标时间序列和基线
- 故障 Case 的时间窗口聚合和去重
- 故障边界传播算法
- 根因候选评分
- 受控 probe 类型和预算
- 证据引用校验
- Incident / 审批 / 知识闭环
- 更多类型 Agent：网络、存储、虚拟化

**汇报时的原则：**

> 不把目标态说成已交付态。  
> 已落地讲“能力基础”，未落地讲“演进路径”。

---

## 18 总结：一句话讲清平台

> OpsAgent 用操作系统智能体把每台服务器的现场事实变成可调度的证据，用控制面把跨主机的异常聚合成故障案例，用访问拓扑先划定故障边界，再通过总调度智能体按证据缺口调度 Agent 补采，最终产出可解释、可追溯、可审批的根因结论。

**三个关键词：**

```text
现场      操作系统智能体
边界      故障定界
闭环      发现 → 调度 → 取证 → 结论 → 处置
```

**结束语：**

> 我们做的不是一个“会回答问题的 AI”，  
> 而是一套“能在真实运维现场组织事实、调度智能体、收敛根因”的系统。
